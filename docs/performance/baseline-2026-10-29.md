# Performance baseline — 2026-10-29

A real k6 run against the Docker Compose stack on a developer laptop. These are measurements, not targets; they
exist to be compared with later runs.

## Environment

| Item | Value |
|---|---|
| Host | Windows 11 laptop, Docker Desktop 29.8 (all containers on one machine, including k6) |
| Stack | `docker compose --profile app` — gateway, Orders, Inventory, Fulfillment (1 instance each), PostgreSQL 17, RabbitMQ 4.1, nginx web |
| Tool | `grafana/k6:1.3.0`, script `tests/performance/k6/baseline.js` |
| Load | 10 VUs for 1 minute: 5 VUs creating orders (`SKU-BULK-001`), 5 VUs reading (order list, stock, dashboard) |
| Raw output | k6 `--summary-export` JSON, kept locally and not committed (it embeds the setup session token) |

## Results — asynchronous processing (the honest part)

Accepting an order is fast because it is one local transaction (order + outbox row). Processing it is a chain of
three consumers. Measured after the run:

| Time | Orders still `PendingInventory` | Orders in `Picking` |
|---|---|---|
| 10 s after the load stopped | 22,861 | 6,610 |
| +60 s later | 11,842 | 17,598 |

- **Sustained end-to-end throughput: ~154 orders/s** reaching `Picking` (9,241 orders in 60 s), versus 539 orders/s
  of intake. The system absorbed the burst in the queues and caught up without errors or lost messages.
- **Peak queue depth:** `orders.integration-events` 13,741 messages, `inventory.integration-events` 4,835.
- **Bottleneck:** the Orders consumer. It handles two events per order (`InventoryReserved`, `FulfillmentStarted`),
  one at a time (a single channel, sequential dispatch), each in its own transaction with an inbox insert and an
  optimistic-concurrency update.

## What this tells us, and what comes next (Phase 6)

1. The outbox did its job: intake latency is independent of downstream speed, and nothing was lost.
2. Consumer concurrency is the next lever. Options, in order of cost:
   competing consumers (more instances — safe because handlers are idempotent through the inbox and the order
   version), `ConsumerDispatchConcurrency` > 1 per instance, then batching publisher confirms in the outbox relay.
3. Queue depth needs to be visible: Phase 6 exports it to Prometheus with an alert on sustained growth.

The heavier profiles (load, stress, spike, soak, concurrent reservations) are planned for Phase 6 and have not been run.
